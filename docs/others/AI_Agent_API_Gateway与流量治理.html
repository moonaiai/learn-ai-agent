Multi-Stage Routing

硬过滤先于评分 — 六阶段路由流程

租户权限 → 能力过滤 → 类型过滤 → 成本约束 → 性能排序 → 最终选择
01租户权限 — 检查租户可用模型白名单，排除未授权模型
02能力过滤 — 按 function_calling / vision / json_mode 等能力标签硬过滤
03类型过滤 — chat / completion / embedding / rerank 类型匹配
04成本约束 — 剩余预算 < 单次调用预估成本则排除高价模型
05性能排序 — 通过过滤的候选集按评分公式排序
06最终选择 — Top-1 + fallback 列表，记录选择理由用于审计
Routing Score

路由评分公式：质量、延迟、可用性、成本、Token 压力、风险

score = wq×quality + wl×latency + wa×availability - wc×cost - wt×token_pressure - wr×risk
Qquality — 模型基准评分 + 业务评测分数，0-1 归一化
Llatency — p50 TTFT 倒数归一化，越快得分越高
Aavailability — 近 5 分钟成功率 EWMA，熔断中为 0
Ccost — $/1K tokens 归一化，越贵扣分越多
Ttoken_pressure — 当前 TPM 使用率 / 配额，接近上限时大幅扣分
Rrisk — 最近 429/5xx 频率，高风险降权

模型别名机制：业务代码使用 "fast-chat" / "deep-reason" 等别名，网关负责解析到具体 provider:model:version。

LoRA Routing

LoRA 路由：adapter_id → base_model → GPU pool → loading status

adapter_id → base_model → GPU pool → loading check → inference
01adapter 注册 — 每个 LoRA adapter 关联 base_model、版本、大小、最大并发
02strict_lora 策略 — 仅路由到已加载目标 adapter 的实例，不回退到 base model
03热加载检查 — 若目标实例未加载 adapter，先触发异步加载再排队等待
04架构拆分建议 — 网关负责 adapter → pool 映射，vLLM 负责 adapter 热加载管理

推荐架构：AI Gateway 做路由决策，vLLM / SGLang 做 LoRA 热加载与推理，职责清晰可独立扩展。

Rate Limiting Algorithm

令牌桶 + 多桶并行：RPM + 输入 TPM + 输出 TPM + 成本 + 租户

估算 Token → 预留配额 → 调用模型 → 记录实际 → 对账归还
01估算 (Estimate) — 用 tiktoken 快速估算输入 Token 数，按 max_tokens 预估输出
02预留 (Reserve) — 同时从 RPM 桶扣 1、Input TPM 桶扣估算值、Output TPM 桶扣 max_tokens
03调用 (Call) — 转发到选定 Provider，开始流式接收
04记录 (Record) — 流式完成后统计实际输入/输出 Token 数
05对账 (Reconcile) — 将预留与实际的差额归还桶中，避免配额泄漏

核心原则：请求前预留输出容量，完成后对账实际消耗。过度预留导致利用率低，预留不足导致超额。

Circuit Breaker

熔断器按 provider × region × model × credential 独立维护

Closed

正常放行，统计失败率

失败率 > 50% (20 次窗口) → Open

Open

拒绝所有请求，直接 Failover

30s 后 → Half-Open

Half-Open

放行 10% 探测流量

3 次连续成功 → Closed

•触发条件 — 连续 5xx、超时率 > 30%、429 持续 > 60s、延迟 p99 > 3x baseline
•粒度维度 — provider × region × model × credential，四维独立熔断
Degradation Strategy

四级降级：同供应商 → 跨供应商 → 能力降级 → 非 LLM 兜底

L1 同供应商降级 同 Provider 切换 region / credential / 副本实例
L2 跨供应商降级 OpenAI → Anthropic → Google，协议适配层自动转换
L3 能力降级 GPT-4o → GPT-4o-mini，牺牲质量保可用性
L4 非 LLM 兜底 模板回复 / 规则引擎 / 缓存命中 / 友好提示

关键洞察：流式输出开始后 Failover 极危险 — 用户已看到部分内容，切换 Provider 会导致语义断裂。应在首 Token 前完成 Failover 决策。

429 Handling

区分三种 429：临时超限 vs 额度耗尽 vs 预算耗尽

A临时超限 (Rate Limited) — RPM/TPM 暂时用完，指数退避后重试。wait = min(base × 2n + jitter, max_wait)
B额度耗尽 (Quota Exhausted) — 月度配额用完，不应重试，直接 Failover 到备用 Provider
C预算耗尽 (Budget Exceeded) — 租户预算上限触达，返回 402 给调用方，不重试不降级
wait = min(base × 2n + random(0, base), max_wait)

黄金法则：重试只在网关层做，Agent 层不应有独立重试逻辑。双层重试 = 重试风暴。

Load Balancing

六种负载均衡策略与综合评分公式

策略原理优势适用场景
加权轮询按权重依次分配简单可预测固定容量部署
Least Busy选择在途请求最少的节点自动负载均衡请求延迟差异大
P2C随机选 2 个，取负载低者避免惊群效应大规模集群
Latency-aware按 p50 延迟倒数加权延迟最优交互式场景
EWMA指数加权移动平均延迟平滑抖动延迟波动大的 Provider
Token-aware按剩余 TPM 配额占比分配配额利用率最优多 Key/多 Provider
LB_score = w1×(1 - busy_ratio) + w2×latency_rank + w3×(remaining_tpm / total_tpm)
SSE vs WebSocket

SSE 是主流 LLM 流式协议，WebSocket 用于实时交互

SSE (Server-Sent Events)

协议：HTTP/1.1+ 单向流

优势：天然兼容代理 / CDN / 负载均衡

格式：text/event-stream, data: JSON

适用：Chat Completion 流式输出

重连：浏览器原生 EventSource 自动重连

VS
WebSocket

协议：全双工长连接

优势：双向实时通信，低延迟

格式：自定义二进制 / JSON

适用：实时语音、协同编辑、游戏 Agent

注意：需要连接管理和心跳机制

•四种超时 — 连接超时(5s)、首 Token 超时(30s)、流式心跳超时(15s)、总请求超时(300s)
Stream Architecture

流式连接六层架构

01Client SDKEventSource / fetch + ReadableStream，自动重连与缓冲
02Gateway ProxySSE 透传，禁用响应缓冲，Transfer-Encoding: chunked
03Session Manager会话关联、断线重连状态、Token 计数器维护
04Router首 Token 前可 Failover，首 Token 后锁定 Provider
05Provider Adapter协议转换：不同 Provider SSE 格式 → 统一内部事件流
06Stream Normalizertext.delta / tool.call / usage / error / done 统一事件模型

关键设计：Gateway 必须禁用 nginx proxy_buffering，否则流式响应会变成批量响应，TTFT 严重劣化。

Two-Tier Cache

L1 精确缓存 + L2 语义缓存：两级命中策略

L1 精确缓存

匹配：SHA-256(prompt + model + params) 精确哈希

命中率：低 (5-15%)，但零误判

延迟：< 1ms (Redis GET)

适用：相同 Prompt 重复调用

TTL：按场景 5min - 24h

+
L2 语义缓存

匹配：Embedding 向量 + cosine similarity > 0.95

命中率：中 (15-40%)，需调阈值

延迟：5-20ms (向量搜索)

适用：语义相似的不同表述

风险：相似 ≠ 等价，需业务校验

查询顺序：L1 精确命中 → L2 语义命中 → Cache Miss → 调用模型 → 同时写入 L1 + L2。

Cache Policy

语义相似 ≠ 业务结果可复用 — 严格定义缓存边界

适合缓存

FAQ 问答 — 固定知识库的标准回答

文档摘要 — 同文档同指令的摘要结果

固定翻译 — 术语表驱动的翻译任务

分类标注 — temperature=0 的确定性输出

不适合缓存

权限相关 — 不同用户应看到不同内容

实时数据 — 股价、天气等时效性信息

敏感信息 — PII / PHI 数据不可共享

写操作 — 工具调用、状态变更不可幂等

缓存键要素

tenant_id — 租户隔离

scope — 缓存作用域

model + version — 模型版本

prompt_version — Prompt 模板版本

tool_hash — 工具定义签名

temperature — 采样参数

Protocol Adaptation

统一 OpenAI / Anthropic / Gemini / Bedrock 的协议差异

01请求格式 — messages[] (OpenAI) vs content[] (Anthropic) vs contents[] (Gemini) vs body{} (Bedrock)
02流式格式 — data: JSON (OpenAI SSE) vs event: (Anthropic SSE) vs chunks (Bedrock) vs array (Gemini)
03工具调用 — function_call (OpenAI) vs tool_use (Anthropic) vs functionCall (Gemini)，参数 schema 差异
04用量字段 — usage.prompt_tokens vs input_tokens vs usageMetadata，命名与位置不同
05错误格式 — error.message vs error.type vs detail，状态码语义不完全一致
统一内部事件模型：text.delta | tool.call | tool.result | usage | error | done

协议适配层的核心价值：业务代码只对接一种格式，Provider 切换对上层完全透明。

Key Metrics

八项核心指标驱动网关运营

TTFT 首 Token 时间 用户感知延迟。p95 < 800ms 为目标。
$/Req 单请求成本 含重试与降级成本的真实单位经济。
Fallback% 降级率 触发 Failover 的请求占比。>5% 告警。
Cache Hit 缓存命中率 L1 + L2 综合命中。目标 >30%。
429 Rate 限流触发率 被限流的请求占比。>1% 需扩容。
TPM Util 配额利用率 当前 TPM / 总配额。>80% 预警。
CB Open 熔断开启数 处于 Open 状态的熔断器数量。
Retry Amp 重试放大因子 总请求 / 原始请求。>1.1 需调优。

Canary Release

七阶段灰度发布：Shadow(0%) → Full(100%)

0% Shadow 复制流量到新模型，对比输出但不上线 质量 < baseline → STOP
1% Canary 极小流量验证，仅内部用户 error > 1% → ROLLBACK
5% Early Adopter 扩展到愿意尝鲜的外部用户 latency > 2x → ROLLBACK
25% Limited GA 稳定运行 24h 后扩大范围 cost > 1.5x → PAUSE
50% Half Traffic A/B 对比新旧模型综合表现 quality < 95% → PAUSE
90% Near Full 保留 10% 旧模型作为对照与回滚备份 any anomaly → ROLLBACK
100% Full GA 全量上线，旧模型配置保留 7 天 monitor 7d → CLEANUP
