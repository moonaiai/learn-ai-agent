Grader Layer 1

确定性 Grader：零成本、毫秒级、每次提交必跑

01

Schema 校验

输出结构是否符合 JSON Schema，字段类型与约束是否满足

02

工具调用断言

必须调用的工具是否被调用，禁止调用的工具是否被触发

03

API 状态检查

下游 API 返回是否 2xx，错误是否被正确处理

04

重复操作检测

同一工具是否被重复调用超过阈值（循环检测）

05

Token 与费用预算

单次任务的 Token 消耗和成本是否超出预算上限

Judge Governance

LLM-as-Judge 四大陷阱必须治理

Position Bias

Judge 倾向于给列表中靠前的选项更高分

对策：随机化选项顺序

Verbosity Bias

更长的回答被评为更好，即使信息密度更低

对策：评分 rubric 明确惩罚冗余

Self-Enhancement

同系列模型给自己的输出打更高分

对策：使用不同厂商模型交叉校验

Judge Drift

Judge 模型更新后评分标准静默漂移

对策：定期跑标定集，固定版本号

低置信度样本自动触发人工复核 · 多模型交叉校验 · 定期校准

Trace-driven Debugging

五步定位任何 Agent 失败

1

业务结果筛选

从任务失败 / 用户投诉 / SLO 告警出发

2

因果链重建

展开完整 Trace 树，还原执行顺序

3

定位首个错误 Span

找到第一个 status=error 或输出偏离预期的节点

4

自动回放

用相同输入 + 固定 seed 重现问题

5

转化回归用例

将此 Trace 加入 Regression Dataset，防止复发

典型陷阱："工具调用成功 ≠ 业务任务成功" — 必须检查业务状态

Case Study · Airbnb

Airbnb：逐样本缓存降噪 + 修复验证当天闭环

01

逐样本缓存降噪

对每个评测样本缓存 Judge 结果，只有输入变化才重新评测，消除噪声

02

微型 LoRA 替代 few-shot

针对高频评测场景训练小型专用 Judge，降低 80% 评测成本

03

修复验证当天闭环

发现问题 → 定位 → 修复 → 重跑评测 → 验证通过，全部在同一天完成

KEY INSIGHT

评测效率决定迭代速度——如果评测要跑一天，修复周期就变成一周

Summary

企业级 Agent 的质量标准

◉可观测性的本质：让每一次失败都有因果链可追溯
