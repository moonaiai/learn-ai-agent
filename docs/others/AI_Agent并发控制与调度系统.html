From QPS to TPM

三个独立限流维度，任一触顶即限制

RPM 请求数 / 分钟 防止连接数爆炸，与模型无关的硬限制
Input TPM 输入 Token / 分钟 Prompt 长度决定预填充 GPU 时间
Output TPM 输出 Token / 分钟 生成长度决定解码 GPU 时间，成本主导
可持续吞吐 = min(RPM, input_TPM / avg_input, output_TPM / avg_output)

关键洞察：输出 Token 成本通常是输入的 3-4 倍，产出 TPM 往往是第一个触顶的维度。

Rate Limiting Algorithms

令牌桶是 LLM API 的最佳默认选择

固定窗口

+ 实现最简单 - 窗口边界突刺 LLM: 不推荐

滑动窗口

+ 平滑边界 - 内存开销大 LLM: 可用

令牌桶

+ 允许突发 + 均匀补充 + 天然适配 Token 计量 - 需预估容量 LLM: 最佳默认

漏桶

+ 输出极其平稳 - 不允许突发 LLM: 批处理场景

自适应并发

+ 自动发现上限 - 需要反馈信号 LLM: 与令牌桶组合
Token Bucket for LLM

多桶并行：RPM + 输入 TPM + 输出 TPM + 成本 + 租户

01桶容量 (burst) — 允许的最大突发量。设为速率的 1.5-2 倍，防止冷启动饥饿。
02补充速率 (refill) — 每秒向桶中添加的 Token 数。RPM 桶按请求计数，TPM 桶按 Token 计数。
03多桶检查 — 发送前必须同时获取 RPM 桶 + Input TPM 桶 + Output TPM 桶的许可，任一不足即等待。
04输出预留 — 请求前按 max_tokens 预留输出容量，完成后按实际消耗对账归还差额。
05流式对账 — 流式响应中逐块累计实际输出 Token，结束后与预留量对比并调整桶余额。

核心原则：请求前预留输出容量，完成后对账实际消耗。过度预留导致利用率低，预留不足导致超额。

Layered Rate Limiting

五层分层限流：全局 → 租户 → Agent → 工具 → 提供商

1 全局层 保护整个平台不超过提供商总配额 500K TPM
2 租户层 每个企业客户独立配额，防止互相干扰 50K TPM
3 Agent 层 单个 Agent 实例的并发上限 10 并发
4 工具层 每种工具调用的独立限制（如搜索 API） 60 RPM
5 提供商层 适配不同 LLM 提供商的限流规则 按提供商
有效并行度 = min(所有层级限制)

事件混合 DAG

Dynamic DAG Safety

动态 DAG 的五道防护：Agent 在执行中创建新节点的失控风险

01 环检测 — 每次添加边时执行拓扑排序验证，发现环立即拒绝并回滚
02 最大深度 — 限制 DAG 最大深度（如 10 层），防止无限递归子任务
03 节点预算 — 设置总节点数上限（如 50 个），超出则强制终止并报告
04 截止时间 — 全局截止时间 + 单节点超时，确保不会无限等待
05 工具授权检查 — 新创建的节点只能使用已授权的工具集，防止权限提升

Bounded Gather 模式：设定扇出上限 + 超时 + 节点预算，在灵活性与安全性之间找到平衡。

Priority Scheduling

策略行为优点缺点推荐场景

Preemption & Cancellation

Agent 任务不能安全地 OS 级抢占 — 协作取消是唯一选择

协作取消
→
await 边界停止
→
撤销排队子任务
→
checkpoint 状态
→
幂等重试
01检查频率 — 在每个 await 点检查取消标志，而非仅在循环头部。LLM 调用前后必查。
02传播规则 — 父任务取消时，递归取消所有子任务，但允许子任务有清理窗口（如 5s）。
03部分结果 — 取消不等于失败。已完成的步骤结果应保留，供重试时跳过。
04幂等保障 — 所有工具调用必须具备幂等键，取消后重试不会产生副作用。
Backpressure

背压控制全景：四道防线层层递进

LINE 1

准入控制

入口处检查系统负载，过载时直接拒绝新请求（HTTP 503），快速失败优于排队超时。

LINE 2

有界队列 + 溢出策略

队列长度有上限。溢出时可选：丢弃最新、丢弃最旧、丢弃最低优先级。

LINE 3

熔断器

下游错误率超阈值时打开熔断，停止所有请求。半开状态逐步探测恢复。

LINE 4

重试预算

全局重试比率 ≤ 10%。超出预算时停止重试，防止重试风暴压垮系统。

每一道防线都独立生效，形成纵深防御。最常犯的错误是只有队列没有准入控制。

Celery

Celery：Python 生态的经典选择

架构Broker + Worker + Result Backend — Redis/RabbitMQ 作为消息队列，Worker 拉取并执行任务。
并发prefork / eventlet / gevent — prefork 适合 CPU 密集，gevent 适合 I/O 密集的 LLM 调用。
优势成熟稳定、生态丰富 — 内置重试、定时任务、优先级队列、结果追踪。
限制无内置状态持久化 — 任务状态丢失后无法自动恢复，长时间工作流需要额外编排。
场景短时任务、后台批处理 — 适合工具调用分发、批量推理、定时清理等场景。
Temporal

Temporal：长时程有状态工作流引擎

架构Workflow + Activity + Worker — Workflow 定义编排逻辑（确定性），Activity 执行副作用（可重试）。
持久性事件溯源 + 自动回放 — 每个 Workflow 步骤持久化，崩溃后从最后完成的 Activity 恢复。
容错内置超时、重试、心跳 — Activity 超时自动重试，心跳检测 Worker 存活，Saga 补偿回滚。
审批Human-in-the-Loop 原生支持 — Workflow 中 await signal("approval") 暂停等待人工审批。
场景Agent 编排的最佳引擎 — 多步骤规划、工具链调用、子代理编排、长时间审批流。

Distributed Locking

协调策略决策优先级：从无协调到数据库事务

1 无协调 操作天然幂等，无需锁。最优选择，尽量让设计走到这一步。
2 乐观并发 版本号/ETag，提交时冲突检测。适合冲突率 <5% 的场景。
3 队列序列化 同一实体的操作串行入队。避免锁但保证顺序，Temporal 内建。
4 租约锁 Redis/Zookeeper 分布式锁 + TTL + 心跳续租 + fencing token。
5 DB 事务 数据库级别的强一致事务。成本最高，仅用于金融级准确性要求。

Semantic Locking

语义锁：锁实体/工作空间/目标，而非仅锁数据库行

场景：两个 Agent 同时对同一客户订单推理 — 数据库行级锁粒度太细，全局锁粒度太粗。

01 实体键锁 — lock("order:12345") 锁定业务实体而非 DB 行，语义清晰
02 意图声明 — Agent 获锁时声明意图（读/写/推理），读-读不冲突，读-写互斥
03 乐观并发 — 推理阶段不加锁，提交时用版本号验证数据未被修改
04 冲突解决 — 版本冲突时：自动重试 → 合并 → 人工仲裁，逐级升级

核心原则：推理阶段宽松，提交阶段严格。让 Agent 自由思考，但写入时强制一致。

Python asyncio

Python asyncio：Agent 开发的默认选择

01asyncio.to_thread — 将同步阻塞的工具调用（文件 I/O、SDK）放入线程池，不阻塞事件循环。
02ProcessPoolExecutor — CPU 密集型操作（如嵌入计算、数据预处理）放入进程池，绕过 GIL。
03TaskGroup + Semaphore — 结构化并发：TaskGroup 管理生命周期，Semaphore 控制并发度上限。
04asyncio.Queue — 生产者-消费者模式，有界队列自动背压。配合 Semaphore 实现限流。
05异常传播 — TaskGroup 中任一子任务异常，自动取消其他子任务。确保不会泄漏协程。

Python Agent 的典型瓶颈不是 GIL，而是 LLM API 延迟。asyncio 是 I/O 密集场景的正确选择。

Go Concurrency

Go goroutine + channel：高吞吐 Agent 服务的利器

01goroutine — 2KB 初始栈，可轻松创建百万级并发。每个工具调用一个 goroutine，调度器自动管理。
02errgroup — 类似 Python TaskGroup，任一 goroutine 失败自动取消 context，传播错误。
03weighted semaphore — semaphore.NewWeighted(N) 按权重获取许可，大模型调用权重高。
04channel + select — 有界 channel 天然背压，select 实现超时和取消的优雅处理。
05GOMAXPROCS — 容器环境下用 automaxprocs 自动适配 CPU 配额，避免过度调度。
Rust Tokio

Rust Tokio：高性能 Agent Gateway 的选择

01spawn_blocking — 同步阻塞操作放入专用线程池，不阻塞异步运行时。类似 asyncio.to_thread。
02JoinSet — 管理一组异步任务的生命周期，支持取消和错误收集。类似 TaskGroup。
03multi-thread runtime — 默认工作窃取调度器，自动在多核间负载均衡。无 GIL 问题。
04tower 中间件 — 限流、重试、超时、负载均衡作为可组合的 Service 层，声明式配置。
05零成本抽象 — async/await 编译为状态机，无运行时分配开销。适合 Gateway/Proxy 层。

Rust 适合 Agent 基础设施（网关、限流器、路由器），不适合 Agent 业务逻辑（快速迭代需求）。

Worker Pool Patterns

分道池：防止后台工作耗尽交互容量

交互道

40% 用户实时请求。最高优先级，严格 SLA（p95 < 3s）。

工具执行道

25% Agent 工具调用。中等优先级，可容忍短暂排队。

子代理道

15% 子代理 LLM 调用。隔离防止子代理风暴影响主代理。

后台道

15% 批量推理、索引构建。低优先级，可降级或延迟。

恢复道

5% 重试、补偿、死信处理。预留容量确保故障恢复不被饿死。

关键原则：交互道永远不被后台工作挤占。即使系统过载，用户实时请求仍有专属容量。

Batching

批量推理：API 批处理 vs 推理引擎连续批处理

API BATCH

模式 — 提交异步批量作业，24h 内返回结果

成本 — 通常为实时价格的 50%

延迟 — 分钟到小时级，不适合交互场景

适用 — 离线评估、数据标注、批量分析

VS
CONTINUOUS BATCHING

模式 — 推理引擎逐步动态组批，实时返回

技术 — vLLM PagedAttention / TGI / TensorRT-LLM

延迟 — 与单请求接近，吞吐提升 2-5x

适用 — 自托管推理、高并发实时服务

使用 API 服务时用批量接口省钱，自托管时用连续批处理提吞吐。两者并非互斥。

Retry & Backoff

指数退避 + 抖动 + Retry-After：重试不应消耗交互容量

01最大重试次数 — 默认 3 次，429 可放宽到 5 次。超过后放入死信队列，不要无限重试。
02截止时间 — 总超时优先于重试次数。即使没到最大重试，截止时间到了就停止。
03幂等键 — 每个请求携带 idempotency-key，服务端去重，确保重试安全。
04取消传播 — 父任务取消后，正在等待重试的子任务立即停止退避并清理。
05熔断器联动 — 重试失败触发熔断器计数。连续失败超阈值时打开熔断，停止所有请求。

公式：delay = min(base * 2^attempt + random(0, base), max_delay)。始终尊重 Retry-After 头。

Observability

并发系统必须追踪的七项核心指标

RPM/TPM 利用率 当前消耗 / 配额上限。>80% 预警。
In-Flight 在途请求数 当前并发数 / 最大并发度。突增预警。
Queue Age 队列等待时间 任务入队到开始执行的延迟。>1s 预警。
TTFT 首 Token 时间 用户感知延迟的关键指标。p95 目标。
429/5xx 错误率 限流和服务错误比率。>0.1% 调查。
Retry Amp 重试放大因子 总请求 / 原始请求。>1.1 需要调优。
$/Success 每成功任务成本 包含重试成本的真实单位经济。
Reference Architecture

生产参考架构：五层调度器职责拆解

1 API 入口 准入控制 + 令牌桶限流 + 认证鉴权 + 请求路由
2 工作流协调器 DAG 编排 + 状态持久化 + Human-in-the-Loop + Saga 补偿
3 调度器 优先级排队 + 分道调度 + 背压控制 + AIMD 自适应
4 Worker 分道 交互道 / 工具道 / 子代理道 / 后台道 / 恢复道

每一层独立可替换：API 层可选 Kong/Envoy，协调器可选 Temporal/Inngest，Worker 可选 Celery/自研。
